# 方案定稿：把想法做成一个「成熟、会被玩、会被传」的 Toy

开发者的想法基本确定后（或用户说「帮我出方案」「我想做一个 xx Toy」），在动手写代码之前走这一步。
它是把通用的「更有野心地完成任务」四步法（高度 → 深度 → 广度 → 定稿）改造成 Toy 专用版：
目标是让方案**比开发者原本想的高一个层次**，同时每一条都落在 Toy 平台真实能做的事情上。

## 0. 先拿到当下的广场数据

```bash
python3 "<toy-maker-dir>/scripts/fetch_square.py" --search <题材关键词1> <题材关键词2>
```

- 关键词用题材和形式（「人格测试」「塔防」「抽卡」「某游戏名」），不用整句。
- 读 `.toy-maker/showcase.md`：同题材已有作品（搜索结果）、本周必玩、上升最快、同类型总榜。
- 抓取失败（退出码 3 = 用了内置快照，2 = 都没有）不要卡住：说明一句，改用 `references/showcase.md` 快照，
  或者用当前环境里任何能打开网页的工具看 https://www.bilibili.com/btoy/square ，都不行就跳过对标，其余照常。
- 用 `references/hit-patterns.md` 的框架解读数据，再读对应类型的 `references/playbooks/<类型>.md`。
- 读 `references/ops-whitepaper.md`（官方《Toy 运营白皮书》）：选题命中率、传播方式的导流倍数、四阶助推门槛、各类型复玩率——方案里的运营部分以它为准。

## 1. 高度：这个 Toy 背后真正的目标是什么

问开发者（已经清楚的不问）：做完希望发生什么？常见的几种，方案重心完全不同：
- **给自己的视频/账号带粉**：重心在视频 ↔ Toy 闭环、关注/三连额外奖励、作者主页跳转。
- **冲广场/本周必玩**：重心在完成度、首屏、更新节奏、选不拥挤的赛道。
- **服务一个圈子**（某游戏玩家、某粉丝群）：重心在准确、好用、回访（收藏、云存档）。
- **参赛/活动**：重心在活动要求（发布时 `--activity`）、截止时间、主题契合。
- **练手/表达**：保持小而完整，别加功能。

写一句「改写后的目标」，必须能在上线后用数据验证（游玩数、次日留存、收藏、评论、绑定视频的播放）。

## 2. 深度：像做过爆款的人那样补齐用户没想到的

对照广场数据和类型手册，逐项检查方案有没有：
1. **对标**：2–3 个同题材/同形式的真实作品（附链接、游玩数、上线天数），各自强在哪、弱在哪；
   你的**差异点**一句话说清。搜不到同题材 = 题材新，说明这是机会也是风险。
2. **首屏 3 秒**：一句话钩子 + 一个动作；说清时长/题数；授权和教程不挡路。
3. **核心循环**：玩家每一轮在做什么、得到什么；为什么会来第二次（存档、收集、每日、更新）。
4. **可传播的产出**：结果卡 / 作品图 / 名次——它长什么样，怎么存下来（`saveImageToAlbum` / 下载 / 二维码）。官方数据：「玩完生成一张图 / 一段话」的 Toy 破 10 万命中率 62%，全类型第一——问一句「玩完有东西可以截图发出去吗」。
5. **视频方案**：官方导流倍数（以图文挂链为 1）横屏视频 8.6 倍、竖屏 5.5 倍——至少 1 条 1 分钟以上横屏演示 + 数条 15–30 秒竖屏爽点切片 + 1 篇带图小站帖；视频下挂绑定、简介和置顶评论贴带 `/index.html` 的完整链接；Toy 内回链视频。
6. **SDK 清单**：每个能力用在哪一步、Web 端怎么降级。
7. **合规预审**：逐条过 `platform-rules.md` §4，尤其是用户输入、昵称、外链、强制关注、版权。
8. **分类与可见性**：选哪个分类（注意「游戏」分类未成年人不能玩）；先「链接访问」自测，**尽快转「公开发布」**——不公开就进不了广场、搜索和推荐。
9. **长线定位**：按官方复玩率判断它是长跑底盘（工具/资料库 49%、小游戏 + 排行榜 32%）还是爆点（热梗 37% 但梗过即走、测试 26% 人均 1.4 次）；底盘型写版本更新计划，爆点型写上线窗口（热梗 3–7 天内）。

## 3. 广度：用几个专业视角挑一遍（每个只用一种方法，不要角色扮演）

- **社区运营**：用广场数据判断这个钩子在 B站语境里是否成立（熟梗、时间节点、同题材是否已饱和）。
- **增长设计**：画出「看到视频 → 进 Toy → 产出结果 → 回到评论区/视频」的路径，找断点。
- **对应类型的产品设计**：按该类型手册检查结构（测试看结果设计、工具看 3 秒出结果、游戏看首局爽点……），防止所有东西都做成游戏。
- **合规审核员（专门挑错）**：假设审核员想打回这个 Toy，他会抓哪一条？逐条给出修改。
- 可选 **技术负责人**：入口 1MB、包体、横竖屏、频率限制、需不需要自建后端（需申请权限）。

## 写方案时的分寸

- 每个建议都要能追溯到：广场数据、类型手册、官方规则之一。没有依据的猜测要标明是建议。
- 不要为了「高一个层次」加无关功能：深度优先于规模。一个打磨好的核心循环胜过十个半成品功能。
- 高游玩但低互动、贴着红线的作品（福利领取、信息差、互助拉人）不作为对标。
- 具体数字（游玩数、日均）标注抓取日期；不要承诺开发者能达到某个流量。
- 确认后再写代码；进入开发后回到 SKILL.md 的工作流第 2 步。
